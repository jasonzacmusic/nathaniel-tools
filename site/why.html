Engineering/The audit

Why these exist

I did not set out to build a suite. I set out to find why three keyboard shortcuts I had used for years were behaving differently on different days. Fourteen custom actions later, nine of them were doing something I had never asked for.

REAPER 7.77 · macOS arm64 16 files audited line by line 68 automated checks

A REAPER custom action is a list of command IDs, run in order. It is one of the best features in the program and it has one property that makes it quietly dangerous over a decade of use: nothing in the interface tells you what a step does. You see a number. A step you added in 2019 because a forum post recommended it is still there in 2026, still running, still doing whatever it does, in a chain you now press two hundred times a day without looking.

The tool that ends that is CF_GetCommandText, which resolves a numeric command ID to its actual name. It should be the first thing anyone reaches for and it is not — I cost myself two wrong bug theories by reasoning about what a number probably meant instead of asking.

Part one — the actions were lying

A key that centred every pan

The complaint was that record-arm “destroyed the mix”. It did. The XOR record-arm chain contained _XENAKIOS_PANTRACKSCENTER. Every press reset the pan on the tracks it touched. There is no reason for a record-arm action to touch pan; it was almost certainly copied in from somewhere years ago to solve a different problem and never removed.

The replacement script is eleven lines and does exactly one thing. The test asserts the pan value is byte-identical before and after.

A key that changed a global preference

Region Switch behaved differently every other press. Step 2 was _BR_OPTIONS_MOVE_CUR_ON_TIME_SEL — a toggle of a global REAPER preference. So the action alternated between two behaviours, and as a side effect it left a setting for the entire application flipped from wherever you had put it.

This is the most instructive bug in the whole audit, because there is no way to notice it. The key mostly works. The preference change is invisible. You conclude REAPER is flaky.

A key that had never run

“Record toggle doesn't work at all” had the least interesting root cause available: it had no key binding anywhere. Not a broken binding — no binding. I had been pressing a key that was bound to something else entirely and attributing the result to the wrong action.

A key that disarmed 452 tracks

Duplicate Track cleared I_RECARM on every track in the project and never restored it. The intent had been narrow — stop the new duplicate inheriting record-arm — and the implementation was global.

On a small session you would never notice. On the 452-track live rig, one press silently destroys the entire record setup, with nothing on screen to tell you it happened. Arm state is now snapshotted by GUID and restored exactly, except for the new duplicates, which stay armed on purpose.

A key that moved the edit cursor to the mouse

Solo Focus had an audition behaviour: on solo, jump the edit cursor to the mouse position and start playback. If the pointer happened to be over the wrong bar — or over a docked window — you lost your place in the session and the transport ran.

That now defaults to off, with the flag and the reasoning at the top of the file. This is the difference between a bug and a decision: the behaviour was intentional once, and the fix is not to delete it but to stop it being the default.

A key that opened the dialog it existed to avoid

Flush Paste was rewritten specifically to replace 40022 (Save project as…, a modal file browser on every single press) with 40026, the silent save.

Except that a silent save on a project that has never been written to disk also opens Save As. On a fresh untitled session the rewrite reproduced the exact bug it was written to remove. It now checks whether the project has a file, and if it does not, skips the save and says why in one sentence.

A marker key that could destroy a different marker

Marker at Bar's predecessor inserted at the raw edit cursor and then ran _BR_CLOSEST_PROJ_MARKER_MOUSE_SNAP. Two problems. It snapped to the arrange grid — set to 0.125 here, an eighth note — and not to the bar. And because it operates on the closest marker to the mouse, it could pick up an existing, unrelated marker and drag it to the pointer, silently.

The replacement computes the true measure boundary from TimeMap_GetMeasureInfo using integer measures, so there is no float drift to accumulate, and inserts there. While the transport is running it uses the play cursor, so markers can be dropped live.

The discovery that decided the architecture

Having found the bugs, the obvious next move is to fix the custom actions and re-import them as a .ReaperKeyMap. That does not work, and the reason it does not work is not documented anywhere I could find. Measured behaviour:

  • An ACT line whose step count matches an existing action of the same name is a complete no-op. REAPER silently ignores it. No error, no warning, no change.
  • An ACT line whose step count differs creates a brand new action named “Name (2)” with a fresh GUID. The original is untouched and still bound to your key.
  • KEY lines always merge correctly.

In other words: a custom action can never be modified by import. You can only replace it with a script and move the key across. That single finding is why this entire suite is ReaScript, and why the keymap files that ship with it contain KEY lines and nothing else.

It also explains a pile of orphaned actions named Region Switch (2) and XOR Record Arm (2) that had accumulated in the action list over the years — the residue of every previous attempt to fix these by import.

Part two — the apps could kill REAPER

It crashes when I delete or modify tracks.

The complaint that turned the audit into a rewrite

REAPER frees a MediaTrack* the instant the track is deleted. Handing a freed pointer to any REAPER API faults inside REAPER's own C++.

Lua's pcall cannot catch that. This is the part worth internalising if you write ReaScript at all. pcall catches Lua errors. A native memory fault is not a Lua error — the host process dies, taking every unsaved project in every tab with it. Two of the three apps had their draw loop wrapped in pcall, which looked like a safety net and was false comfort.

Both apps cached raw track pointers in their row list and dereferenced them every frame to draw. Deleting, undoing or reordering a track with the window open was a guaranteed crash, not an intermittent one.

Stem Print had the worse version: its restore pass wrote through pointers captured before a multi-minute render, and that pass ran outside the error handler. A fault part-way through would leave the remainder of the session stuck at unity gain and centre pan, silently, with the log reporting a completed render.

The fix, and why it is a library

GetTrackGUID is the only stable identity in REAPER. It survives delete, undo, reorder, tab switching and save-reload. So: store GUIDs, resolve them to pointers immediately before use, validate with ValidatePtr2, and never hold a pointer across a defer frame.

That work already existed — in exactly one of the three apps, where it had been written to fix a crash, and from where it had never been copied. Pointer safety was per-app folklore. It is now Nathaniel Tools/lib/nt_safe.lua, with the reasoning written into the file so the next person does not have to rediscover it the expensive way, and every app in the suite is built on it.

It was proved rather than argued: with a window open on its track list, a track was deleted through the API. Old code, guaranteed crash. Observed: the row rendered as a red (deleted) tombstone and REAPER kept running.

Part three — three APIs that are not what they look like

1. The change watchdog that had never fired

All three apps watched for project changes with GetProjectStateChangeCount. It was probed directly: 

insert a track   -> 8
rename a track   -> 8
delete a track   -> 8

It does not move for track changes. Which means every auto-refresh in the suite had never fired once — including Track Settings Transfer's “Auto-sync”, whose own header claimed it rebuilt the list whenever you added, deleted or renamed a track. Delete a track in the source project and the list just sat there until you hit Rescan.

I only caught it because the crash fix looked broken: after deleting a track the row showed a tombstone instead of disappearing, and a renamed track still read “Track 3”. The tombstone was the safety net working correctly. The refresh behind it had been dead the entire time.

All apps now diff a cheap signature of the track list — count, GUID, name, folder depth — throttled to four times a second, which stays free even on the 452-track rig.

2. ValidatePtr2 rejects 0

0 is ReaScript's standard shorthand for “the current project”. Almost every REAPER API accepts it. ValidatePtr2 does not — pass it 0 and it returns false.

Which means the guard if projAlive(0) then, written in the ordinary idiom, silently returns false for everything and the app does nothing at all. The harness caught this on its first run against the new safety library. Any future app using the normal idiom would have hit it.

3. TimeMap_GetDividedBpmAtTime reports the wrong tempo

It returns the project-start tempo regardless of the position you pass, even after UpdateTimeline(). It reported 120 at a point where the measure map said 140. The consequence in practice was that the tempo dialog prefilled the wrong BPM as soon as a project had more than one tempo marker.

The order that actually works: TimeMap_GetMeasureInfo(0, m) — the sixth return value is the tempo — then TimeMap_GetTimeSigAtTime, then Master_GetTempo as a last resort.

And the one that broke the fix for the fix

The complaint here was “tempo is very tough to lock”. My first theory was that SetTempoTimeSigMarker with ptidx = -1 stacked duplicate markers. Measured, in test pass 5, verbatim from the results file: 

ptidx=-1 on an occupied bar: ok=true  2 -> 2 markers, bar6 now 150.0 bpm
PASS  Tempo: ptidx=-1 on an occupied bar REPLACES, does not stack

So the theory was wrong. The real mechanism was the old chain's step 40256, which inserts a tempo marker at the raw, unquantized edit cursor. Every press lands a few milliseconds from the last one, so the tempo map accumulates near-duplicates that all look like they are on the same bar and fight each other. Quantize the insert to the bar line and the cause disappears.

Then the fix silently did nothing, because of this: 

[1] ok=true tpos=10.0 mpos=5 bpos=1e-11 bpm=140.0 sig=4/4 lin=false

GetTempoTimeSigMarker returns beatpos = 1e-11, not 0, for a marker sitting exactly on a bar line. So the obvious locate rule — if measurepos == bar and beatpos == 0 — never matches, ever. The first version of the fix found nothing and inserted instead of editing, which is the same bug wearing a different hat. Match with a tolerance and cross-check on time.

A bonus: the harmless step that was one character from a disaster

Flush Paste's chain contained a blind press of 41052. CF_GetCommandText says: 

41052 = Item edit: Enable relative grid snap     <- a SETTER, idempotent
41053 = Item edit: Disable relative grid snap
41054 = Item edit: Toggle relative grid snap
1157  = Options: Toggle snapping

41052 enables. It is idempotent, so pressing it blind is harmless. Had anyone helpfully “fixed” it to 41054 — which is what it looks like it should be — it would have flipped relative snap on every single press.

Its state is also unreadable by the obvious means: GetToggleCommandState(41052) returns -1, so any guard of the form if GetToggleCommandState(41052) ~= 1 is always true. And it is not in the project file either — the GRID line was byte-identical across toggles, because the setting is global, not per project. The only readable source is SWS: SNM_GetIntConfigVar("relsnap", 0).

How any of this is known

Not by watching. The ReaScript console is effectively unreadable through a screenshot and impossible to assert against. Everything here was established with a file-based harness: a Lua script registered as an action, which runs each script under test, asserts project state, and writes PASS / FAIL lines to a text file. Then you read the text file.

Files are the only reliable channel between REAPER and anything outside it.

The harness builds its scratch project in its own tab and closes it afterwards, so it never touches the project you had open. It registers all sixteen files, compiles each one, deletes a track behind an app's back and asserts that every safe accessor returns a clean default rather than faulting, checks the change signature moves on delete, exercises the folder normaliser, and returns you to the tab you started on. 

$ lua tests/hierarchy_test.lua
31 passed, 0 failed

REAPER 7.77, in-app harness
68 passed, 0 failed

Two of the failures in the very first pass were not bugs at all: this machine has a default track FX chain, so every newly inserted track already carries a plugin, and my assertions had counted on zero. Any test that counts FX has to probe the baseline at runtime. Pass four came back 11 passed, 5 failed and told me that two of my theories were wrong — which is the most useful result the harness has produced, and the reason the two paragraphs above say “my first theory was wrong” instead of quietly not mentioning it.

The ledger

What is proven, and what is not. This is the part most tool sites leave out.

ClaimEvidenceStatus
The apps cannot crash REAPER on track delete Harness deletes a track behind the app's back and asserts clean defaults; reproduced by hand with the window open. Proven live
Folder edits cannot leave a folder unclosed 31 pure-Lua checks on the level arithmetic, runnable without REAPER, including a regression test for the one real bug found. Proven
The MIDI writer produces valid Standard MIDI Files Generated file parsed back with an independent reader; chunk lengths, tempo, time signature and every note survived exactly. Proven
Change detection fires on insert, rename and delete Verified live: renaming a track updates instantly, a deleted row disappears cleanly. Proven live
The three modal keyboard actions behave correctly Cannot be automated — they open dialogs. Reviewed line by line; not yet hand-verified end to end. Reviewed only
Stem Print's render pass is correct Restore path and pointer safety tested. No full multi-minute print of a real session has been checked file by file. Not verified
Palette & Look's naming and palette surfaces Compile clean and are reviewed. Not exercised end to end in a real session. Not verified
StageRig switches patches indistinguishably from MainStage Version 0.1.0 exists and passes 18 checks on a bench. It has never been played on a stage. Not claimed

That last row is the point of this page. Everything here is free and open source, so the only thing worth anything is whether you can trust the description. Which means the descriptions have to include the parts that are not finished.
