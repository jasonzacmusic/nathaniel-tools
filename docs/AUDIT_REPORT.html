Verified live in REAPER 7.77 — not just reviewed

Everything below was run inside REAPER on this Mac. The crash test builds a scratch project in its own tab, deletes a track behind the app's back, then deliberately touches the freed pointer — the exact sequence that used to kill REAPER. It now returns clean defaults and REAPER keeps running. I also reproduced it by hand in Palette & Look with the window open: the deleted row disappears cleanly instead of taking REAPER down.

The crash you kept hitting

You reported it as “it crashes when I delete or modify tracks.” It was real, it was guaranteed, and it was in two of the three apps — not the one that had already been hardened.

CrashFixed Palette & Look held pointers to deleted tracks

The track list stored REAPER's raw MediaTrack* and read it again on every frame to draw the colour swatches. REAPER frees that pointer the instant you delete a track. Deleting, undoing, or reordering a track while the window was open handed a dangling pointer straight into REAPER's C++ and killed the whole application — taking any unsaved project with it.

Why the safety net didn't catch it: the drawing code was wrapped in pcall, which looks protective but cannot catch a native memory fault. It was false comfort.

Fix: rows now store the track's GUID, which survives delete, undo, reorder and reload. The pointer is looked up and validated immediately before each use. A deleted track shows as a red (deleted) tombstone instead of crashing, and a watchdog resyncs the list the moment the project changes. Palette and Look.lua

CrashFixed Stem Print could crash and leave your faders wrong

Same stale-pointer bug, but worse. Stem Print sets volume to unity and pan to centre before rendering, then restores everything afterwards. A render takes minutes. If any track was deleted in that window, the restore pass wrote through freed memory — and because that pass ran outside the error handler, a failure part-way through would leave the rest of your session stuck at unity gain and centre pan with no warning.

Fix: snapshots key on GUID and are re-resolved after the render. A track that genuinely vanished is skipped and reported in the log rather than written through. Stem Print and Handoff.lua

Worth knowing: this app was never registered as an action in REAPER, which is exactly why nobody ever hit this. It has, in effect, never been run.

The import-direction bug you described

“Choosing one session and importing from another doesn't work, while vice versa works.” Found it — and it's a one-line cause with a genuinely confusing symptom.

Fixed Reversing the direction emptied the target list

Picking a new From project correctly removed it from the To list — nothing may be its own target. But nothing ever took its place. So swapping A→B into B→A left zero targets ticked, the app cleared its focus, and the entire track list vanished behind “Select a target project above.”

One direction looked perfectly fine and the other looked broken, which is precisely what you described. Nothing was actually wrong with the transfer engine — you just couldn't get to it.

Fix: a swap is now a swap. Promote a target to source and the old source automatically takes its place as target. I also added a ⟷ Swap button so reversing direction is one click. Track Settings Transfer.lua

Three things quietly changing your session

None of these crash. All of them change state you didn't ask them to change — the kind of thing that costs you a take.

SeriousFixed Duplicate Track disarmed your entire session

Shift+D cleared record-arm on every track in the project and never put it back. The intent was only to stop the new duplicate inheriting record-arm. On a 452-track live rig, one press silently destroyed the whole record setup with nothing on screen to tell you.

Fix: arm state is snapshotted by GUID, then restored exactly — except for the new duplicates, which stay armed as intended. NPH/NPH_Duplicate Track.lua

Fixed Solo Focus hijacked the transport

A to solo also moved the edit cursor to wherever your mouse happened to be and started playback. If the pointer was over the wrong bar — or over a docked window — you lost your place in the session and the transport ran.

Fix: that audition behaviour now defaults to off. The flag is at the top of the file if you ever want it back. NPH/NPH_Solo Focus.lua

Fixed Flush Paste could pop the very dialog it exists to avoid

The whole point of the rewrite was replacing Save As with a silent save. But a silent save on a project that has never been saved to disk also opens the Save As dialog. On a fresh untitled session, Cmd+Ctrl+V still ambushed you with a file browser.

Fix: it now checks whether the project has a file on disk. If not, it skips the save and tells you plainly why, in one sentence. NPH/NPH_Flush Paste.lua

Found while testingFixed Every “auto-refresh” in the suite was dead

All three apps watched for changes using REAPER's GetProjectStateChangeCount. I probed it directly: it does not move when you insert, rename, or delete a track. It sat on 8 through all three operations.

So every watchdog built on it had never fired once. Track Settings Transfer's “Auto-sync” — described in its own header as rebuilding whenever you add, delete or rename a track — has never actually done that. Delete a track in the source project and the list just sat there until you hit Rescan.

I caught this because the fix looked like it wasn't working: after deleting a track, Palette showed a tombstone instead of removing the row, and a renamed track still read “Track 3”. The tombstone was the safety net doing its job — but the refresh behind it was broken, and had been all along.

Fix: all three apps now diff a cheap signature of the track list (count + GUID + name + folder depth), throttled to 4× a second so it stays free even on a 452-track session. Verified live: renaming a track now updates instantly, and a deleted row disappears cleanly.

Your toolbar — the thing you asked about

Needs your click The MIDI Render button still runs the old broken action

I checked every custom action against your keys and your toolbar. Of the fourteen originals, thirteen were properly retired. One is still live — and it's the one you use most.

Your main toolbar's Custom: Midi Render is still the original chain _SWS_SAFETIMESEL 40849. The keyboard shortcut was migrated to the fixed script; the toolbar button never was. So every time you render MIDI from the toolbar, you get the old unguarded behaviour.

I can't change this safely while REAPER is running — it keeps the toolbar in memory and would overwrite my edit on quit. It's a 20-second fix and I've written the exact steps below.

New: MIDI Batch Export

New app Seven MIDI files at once, numbered, in one pass

You asked how to render seven MIDI files with contiguous names. You couldn't — REAPER's Export project MIDI writes one file, from a time selection, behind a modal dialog. Seven files meant doing it seven times and typing seven names.

So this doesn't use that action at all. It reads the MIDI data directly and writes each Standard MIDI File itself, which is what makes a batch possible.

Export fromSelected items · all items on selected tracks · regions · every MIDI item
NamingPattern with $num $name $track $project $bpm, a start number and digit padding — so Riff 01 - Intro through Riff 07 - Outro in one press
SafetyShows the exact filename each row will write before you commit, and refuses to run if two rows would collide and silently overwrite each other
FidelityTempo and time signature written as meta events, so files open at the right speed in Logic, MuseScore or Sibelius

Verified, not assumed: I generated a test file and parsed it back with an independent MIDI reader. Chunk lengths, tempo, time signature and every note's pitch and timing survive the round trip exactly. NPH/NPH_MIDI Batch Export.lua

New A shared safety spine, so this class of crash can't come back

The pointer-safety work existed in exactly one app and had never been copied to the others — which is why two of three could crash. It's now a shared library every app builds on, with the reasoning written into the file so the next person doesn't rediscover it the hard way. NPH/lib/nph_safe.lua

The standing regression gate

Any time a script changes, run Script: _harvest_scripts.lua from the action list. It registers everything, compiles every file, and re-proves the crash-safety guarantees against a scratch project in its own tab — then writes PASS/FAIL to _nph_results.txt. It never touches the project you have open.
